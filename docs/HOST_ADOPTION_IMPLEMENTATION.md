# DKC2/DKC3 host ports — September 6, 2026

Implemented the four focused ports identified in [the source review](HOST_ADOPTION_REVIEW.md). DKC1 retains its independent fixed 60 Hz cartridge producer and immutable Metal presentation queue. No interpolation or second cartridge frame is used to fill a 120 Hz presentation slot.

## Implemented behavior

- **Refresh qualification:** `desktop_refresh.[ch]` requires eight consecutive observations before changing an integer 60 Hz divisor (1–4, within 2%). Isolated late callbacks no longer switch 120 Hz output to a one-repeat policy. Incompatible refresh uses absolute presentation targets. Visibility changes reset qualification. Guest timing remains the existing Mach pacer.
- **Audio drift correction:** `desktop_audio_rate.[ch]`, adapted from the identical DKC2/3 modules, resamples the combined SPC + MSU-1 PCM by at most ±0.5%. Queue fill is smoothed at 0.02; the target includes the obtained SDL device pull size and existing preroll. Reset, load, pause, rewind, and fast-forward clear the host resampler/device timeline. The host consumes canonical audio even when muting fast-forward or discarding an overflowing queue. It never runs extra guest frames to prime audio. The adjustment can slightly change pitch.
- **Native controls:** **Game → Controls and Assist…** (Command-comma) offers independent keyboard/gamepad bindings, deadzones, and source selection for two players. The first player's default remains keyboard plus gamepad. Player 2 defaults to None. Pads are assigned to configured gamepad sources in connection order; the left analog stick also drives mapped D-pad directions. Settings persist through NSUserDefaults. Reserved function keys retain their debugger actions. Enabled assist bindings are excluded from guest bindings; Command shortcuts are not sent to the game. The existing first-controller asynchronous rumble worker is preserved.
- **Optional Assist:** enable it in Controls. Hold **Backspace** to rewind or **Tab** for **3× fast-forward**; default pad triggers provide the same actions. Fast-forward advances three canonical frames, with their renderer/diagnostic work, before submitting the final endpoint. Its sound is muted. Rewind captures every third frame and restores both a native memory snapshot and the captured pixels, without rerunning the stateful renderer backward. A 128 MiB history budget and a maximum of 300 slots bound allocation. Sparse snapshots vary in size: slots use a length prefix and capacity bands, rather than resetting history whenever a serialized size changes. The tested 512 KiB snapshot capacity plus pixels gives **161 slots, about 8.05 seconds**. Larger states reduce this span. A capacity increase starts a new history.

Loads and rewind abandon queued Metal packets, clear scheduled gameplay input, reset audio/MSU-1/haptics, and re-anchor the flight recorder. Changing aspect or explicitly loading a quicksave clears rewind history. Exporting while rewinding starts from the restored timeline. Flight exports now preserve both packed 12-bit controller words with six-digit masks; their verifier continues to accept old three-digit recordings.

## Validation

Evidence is local and ignored under `build/repros/host-adoption-20260906/`. No ROM, private state, or generated game code is included in source changes.

- Both Mac and headless targets build. The full Python suite passes **239 tests with one skip**, including compiled refresh, audio, input, rewind, renderer-boundary/HDMA-row, and cache-window models.
- Native Controls UI was opened, changed (B → C, deadzone 25 → 30, Player 2 → Gamepad, Assist enabled), saved, and reopened with those values retained. Restore Defaults was exercised in the separate QA bundle. The test caught and fixed duplicate SDL key names dropping the Return binding. See `controls-saved.png`.
- Neutral and moving assist runs each advanced 480 canonical frames, popped 30 three-frame snapshots, and finished 390 frames beyond the root. Final WRAM, VRAM, CGRAM, both OAM hashes, and native-center hash match independent 390-frame replay oracles. The moving oracle uses the retained 240 input frames followed by 150 neutral frames, verifying that abandoned playback inputs are cleared. See `assist-moving/`, `moving-rewind-oracle/report.json`, and `rewind-oracle.json`.
- A 90-frame live recording with both controller words set (`081081`) exports six-digit input masks and passes independent flight-bundle replay verification. See `ports/verification.json`.
- A five-minute, 18,000-frame audio/pacing run includes a controlled 120 ms host stall at frame 240. No audio submissions were dropped and there were no internal audio underflows. Queue range after warmup was 533–2,772 frames; correction stayed in 0.99918729–1.005. Two long-stall recoveries include startup and the injected stall. CPU interval p99 was 16.6703 ms. See `stall-long/` and `host-metrics.json`.
- The baseline had **116 repeat-goal changes in 1,800 frames**. Both the 3,600-frame candidate and the 18,000-frame run had **zero**, using divisor 2 after warmup. Physical scanout still varies and these desktop captures include occluded/skipped drawables. This is evidence that the qualification policy no longer flaps, not a claim that all ProMotion microstutter is solved. The existing compositor issue remains open.
- Save/load continuity and retained-versus-cold transition checks pass; see [the aquatic investigation](WIDESCREEN_WATER_FLASH.md). The final signed application was launched and inspected.

Real two-controller hardware, hotplug under Bluetooth load, audible MSU-1 evaluation, audio-device replacement, and physical 60/144/240 Hz monitors were not available in this session. Their mappings/divisors are covered by backend-independent tests; do not mistake those for hardware acceptance. Five minutes of audio is a bounded device test, not an overnight drift measurement.

The normal app includes the host ports. The separate **DKC1 Widescreen Candidate.app** also enables the experimental aquatic fixes and starts paused at the preserved clean-entry state. Source and engine edits remain uncommitted for user verification.

The final candidate opens through LaunchServices with private, hash-verified copies of the ROM and entry state under `~/Library/Application Support/Flat2VR/DKC1Recomp/candidate-inputs/20260906/`. This avoids the observed startup file-access error for the Downloads path. These inputs are outside the application bundle and repository source. `final-candidate-manifest.json` records the signed executable, exact paths, hashes, and final paused process; `final-window.png` captures its actual window.
